Context — How Services Reach Your Code

Lesson 001 — What Context is, how services are stored, and how yield* retrieves them

The problem: passing services around

Imagine every function that needs a database has to accept it as a parameter. And every function calling that function must thread it through too. This is the dependency threading problem: 

function getUser(id: string, db: Database) {
  return db.query("SELECT * FROM users WHERE id = ?", [id])
}

function handleRequest(req: Request, db: Database, logger: Logger) {
  logger.log("handling request")
  const user = getUser(req.params.id, db) // threading db through
  // ...
}

// At the top, you need all services wired
handleRequest(req, dbInstance, loggerInstance)

This doesn't scale. You either thread everything manually, or bundle services into a grab-bag "environment" object that has no type safety.

✗ Manual threading

Every function carries all dependencies. Adding a service means changing every function signature in the chain.

✓ Context

Functions declare which services they need via types. The runtime provides them automatically. Adding a service only changes the functions that actually use it.

What Context actually is

A Context is a typed heterogeneous map. At runtime, it's just a Map<string, any>. At the type level, it tracks exactly which services are present.

Context<Services> Runtime: Map { Type level: "Database" → { query: ... } Services = Database | Logger | Config "Logger" → { log: ... } ^-- tracked by the type system "Config" → { port: ... } Can't compile if a needed service is missing }

Step 1: Define a service tag

A tag is the key into context. It's an identifier (a string) plus a Shape describing the service's interface. In v4, use Context.Service: 

import { Context, Effect } from "effect"

// Function-style (simplest):
const Random = Context.Service<{
  readonly next: Effect.Effect<number>
}>("MyRandomService")

// Class-style (preferred for larger apps):
class Database extends Context.Service<Database, {
  readonly query: (sql: string) => Effect.Effect<unknown[]>
  readonly execute: (sql: string) => Effect.Effect<void>
}>()("Database") {}

The tag itself is an Effect. When you yield* Database, you're telling the runtime: "look up "Database" in the current context and give me the value stored there."

A tag is a typed key. The string "Database" is the runtime identity. The Shape ({ query, execute }) is the compile-time contract. The tag bridges the two.

Step 2: Use a service via yield*

Inside Effect.gen, yield* extracts the service from context. The type of the enclosing effect automatically gains the service's identifier in its R parameter: 

const program = Effect.gen(function* () {
  const db = yield* Database      // Look up "Database" in context
  const users = yield* db.query("SELECT * FROM users")
  return users
})
// Type: Effect<unknown[], never, Database>
//                                   ^^^^^^^^
//                      "I need a Database to run"

Step 3: Provide a service

Before you can run an effect that needs a service, you must provide an implementation. The simplest way is Effect.provideService: 

import { Effect, Context } from "effect"

const runnable = program.pipe(
  Effect.provideService(Database, {
    query: (sql) => Effect.succeed([{ id: 1, name: "Alice" }]),
    execute: (sql) => Effect.succeed(undefined)
  })
)
// Type: Effect<unknown[], never, never>
//                         Database requirement → satisfied

The three concepts in one table

ConceptWhat it isAnalogy
Service A reusable component with a specific interface The thing you need (database, logger, etc.)
Tag Unique identifier + type describing the service The key on your keyring
Context Typed map from tags to service values The keyring holding all keys and their services

What happens inside Effect.gen when you yield* a tag

This is the core mechanism you need to internalize. When you write: 

Effect.gen(function* () {
  const db = yield* Database
  // ...
})

The generator runtime does this behind the scenes:

  1. Pause the generator at yield* Database
  2. Look at the current fiber's context (a Context value)
  3. Call context.mapUnsafe.get("Database")
  4. If found: resume the generator with the service value
  5. If missing: the type system would have caught this before runtime

Building Contexts by hand

You rarely build Contexts manually (Layer does it for you), but understanding the raw API clarifies what's happening: 

import { Context } from "effect"

class Config extends Context.Service<Config, {
  readonly port: number
}>()("Config") {}

// Create a context with one service
const ctx1 = Context.make(Config, { port: 8080 })
// Context<Config>

// Add another service
const ctx2 = Context.add(ctx1, Database, {
  query: (sql) => Effect.succeed([]),
  execute: (sql) => Effect.succeed(undefined)
})
// Context<Config | Database>

// Retrieve a service
const cfg = Context.get(ctx2, Config) // { port: 8080 }

Context.make creates a context with one service. Context.add adds another. Context.get retrieves by tag. Context.mergeAll combines multiple contexts. Context.empty() creates an empty one.

The effect-channel: tags are also Effects

A tag satisfies the Effect<Shape, never, Identifier> interface. This is why you can yield* it: 

// A tag IS an Effect:
class Database extends Context.Service<Database, Shape>()("Database") {}
//    satisfies Effect<Shape, never, Database>

// So this works:
const db = yield* Database        // Same mechanism as yield* anyEffect
const x  = yield* Effect.succeed(42) // Both retrieve from context / produce value

When the runtime encounters yield* tag, it retrieves the service from the fiber's context (or fails with a type error at compile time if the service was never provided).
