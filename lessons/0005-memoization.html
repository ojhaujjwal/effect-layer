Layer Memoization — Sharing & Freshness

Lesson 005 — How Effect shares layers, the reference-identity footgun, and opting out

The problem: building the same layer twice

Your dependency graph is a tree. Branches can converge on the same dependency. If UserRepo and OrderRepo both need Database, you don't want two database connections.

UserRepo OrderRepo │ │ ├── needs Database ─┤ │ │ ▼ ▼ ┌──────────────┐ ┌──────────────┐ │ Database │ │ Database │ ← WRONG — two pools │ connect() │ │ connect() │ └──────────────┘ └──────────────┘

Layer memoization solves this: the same layer instance is built exactly once, even when it appears multiple times in the composition.

How it works: reference-identity memoization

Effect tracks which Layer instances have been built using a MemoMap — essentially a Map<Layer, Context> backed by a SynchronizedRef. When a layer is about to be built, the runtime checks:

  1. Is this exact layer instance already in the MemoMap?
  2. If yes — reuse the cached context. Skip construction.
  3. If no — build it, store the result, increment the reference count.
The key word is "instance." Memoization works by object reference (===), not by structural equality. This is the footgun.

The footgun: parameterized layer constructors

If you create a layer by calling a function, each call produces a different object reference. The MemoMap sees them as different layers. Each gets built independently:

Wrong: two different layer instances, two database pools 
// postgresLayer is a function that returns a new Layer each time
declare const postgresLayer: (opts: { url: string }) => Layer<Database>

const AppLayer = Layer.merge(
  UserRepoLive.pipe(
    Layer.provide(postgresLayer({ url: "postgres://localhost/db" }))
  ),
  OrderRepoLive.pipe(
    Layer.provide(postgresLayer({ url: "postgres://localhost/db" }))
  )
)
// postgresLayer({...}) called twice → two different references → TWO pools!
Right: bind to a constant first 
// Store the result in a module-level constant
const DatabaseLive = postgresLayer({ url: "postgres://localhost/db" })

const AppLayer = Layer.merge(
  UserRepoLive.pipe(Layer.provide(DatabaseLive)),
  OrderRepoLive.pipe(Layer.provide(DatabaseLive))
)
// Same reference used twice → memoized → ONE pool shared

Rule: always store parameterized layer results in a const before using them in multiple places in your graph.

v4 change: shared MemoMap across provide calls

In v3, each Effect.provide call created its own isolated MemoMap. Two provide calls with the same layer would silently build it twice.

In v4, the MemoMap is shared across all Effect.provide calls on the same fiber. The same layer instance is built once regardless of how many provide calls reference it: 

const program = Effect.gen(function* () {
  const svc = yield* MyService
  return svc.value
})

const main = program.pipe(
  Effect.provide(MyServiceLayer, consoleLog("first provide")),
  Effect.provide(MyServiceLayer, consoleLog("second provide"))
)
// v3: "Building MyService" logged TWICE
// v4: "Building MyService" logged ONCE — MemoMap is shared
Still prefer one provide. The shared MemoMap is a safety net, not a substitute for proper layer composition. Compose your layers first, then provide once at the top.

Opting out: Layer.fresh and { local: true }

Sometimes you want a layer rebuilt — for test isolation, or independent resource pools. Two mechanisms:

Mechanism What it does Use for
Layer.fresh(layer) Wraps a layer so it bypasses the MemoMap entirely One specific layer must never be shared
Effect.provide(layer, { local: true }) Builds the layer with its own private MemoMap An entire subtree must be isolated

Layer.fresh

const main = program.pipe(
  Effect.provide(MyServiceLayer),           // built ONCE
  Effect.provide(Layer.fresh(MyServiceLayer)) // built AGAIN (fresh MemoMap)
)
// "Building MyService" logged TWICE

Effect.provide with { local: true }

const main = program.pipe(
  Effect.provide(MyServiceLayer),                    // shared MemoMap
  Effect.provide(MyServiceLayer, { local: true })     // private MemoMap
)
// "Building MyService" logged TWICE — local creates its own scope

local: true is preferred for test suites — provide the test layer with { local: true } so each test gets fresh resources.

Memoization + Scope = automatic cleanup

When a layer is memoized, the MemoMap tracks a reference count. Finalizers (cleanup) are registered on the scope. When the scope closes, all finalizers run. This means scoped resources (database connections, file handles) are properly released — and only once, because the layer was built only once. 

const DatabaseLive = Layer.effect(Database,
  Effect.gen(function* () {
    console.log("connecting...")
    const connection = yield* acquireRelease(
      connectToDb(),                    // acquire
      (conn) => Effect.sync(() => conn.close())  // release
    )
    return { query: (sql) => connection.query(sql) }
  })
)

// Even if DatabaseLive appears 5 times in the graph:
// - "connecting..." is logged ONCE
// - conn.close() is called ONCE when the scope ends
