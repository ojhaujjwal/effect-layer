Testing with Layers

Lesson 010 — Mock layers, test isolation, and the vitest integration

The problem Layer solves for testing

Without Layer, testing code that depends on Database, Logger, etc. means either: creating real resources (slow, fragile) or manually threading mock objects through every function signature. With Layer, you swap the whole dependency graph in one place.

Production: Testing: program program │ │ │ Effect.provide(AppLayer) │ Effect.provide(TestLayer) │ │ ├─ ConfigLive (real) ├─ ConfigTest (fake) ├─ LoggerLive (real) ├─ LoggerTest (silent) ├─ DatabaseLive (pool) ├─ DatabaseTest (in-memory) └─ UserRepoLive (real) └─ UserRepoLive (uses test deps)

Pattern #1: Layer.mock — partial mocks

The simplest approach. Only implement the methods you actually use in your test. Any unimplemented Effect methods will throw at runtime, loudly, so you know exactly what's missing: 

import { Context, Effect, Layer } from "effect"

class UserService extends Context.Service<UserService, {
  readonly config: { apiUrl: string }             // non-Effect: required
  readonly getUser: (id: string) => Effect.Effect<unknown, Error>
  readonly deleteUser: (id: string) => Effect.Effect<void, Error>
  readonly updateUser: (id: string, d: object) => Effect.Effect<unknown, Error>
}>()("UserService") {}

// Only implement what's needed — the rest throws if called
const UserServiceTest = Layer.mock(UserService, {
  config: { apiUrl: "https://test-api" },         // required (non-Effect)
  getUser: (id) => Effect.succeed({ id, name: "Test" }) // mock
  // deleteUser & updateUser omitted → throw UnimplementedError if called
})

Layer.mock uses PartialEffectful<S>: Effect functions and Stream/Channel values become optional so you only stub what's exercised. Non-Effect properties (like config) are still required.

Pattern #2: Manual test layers

When you need mutable state or setup logic, a manual test layer gives you full control: 

class Database extends Context.Service<Database, {
  readonly query: (sql: string) => Effect.Effect<readonly unknown[]>
}>()("Database") {}

// In-memory database for testing
const DatabaseTest = Layer.succeed(Database, {
  query: (sql) => Effect.succeed([
    { id: 1, name: "Alice" },
    { id: 2, name: "Bob" }
  ])
})

// Or with mutable state
const DatabaseTest = Layer.sync(Database, () => {
  let records: Record<string, unknown>[] = []
  return {
    query: () => Effect.succeed(records),
    execute: (sql: string) => {
      if (sql.includes("INSERT")) records.push({})
      return Effect.void
    }
  }
})

Pattern #3: it.effect — the test runner

it.effect from @effect/vitest runs an Effect in a test. It auto-provides Scope and test services (TestClock, TestConsole): 

import { it } from "@effect/vitest"
import { Effect } from "effect"

it.effect("fetches user by id", () =>
  Effect.gen(function* () {
    const db = yield* Database
    const user = yield* db.query("SELECT * FROM users WHERE id = '1'")
    expect(user).toEqual([{ id: 1, name: "Alice" }])
  }).pipe(
    Effect.provide(DatabaseTest)  // ← fresh layer per test
  )
)
Each it.effect runs with a fresh Scope. Layers provided inside the test body are rebuilt for each test. State from one test never leaks into the next. This is the default — no configuration needed.

Pattern #4: it.layer — suite-shared layers

When a layer is expensive to build (real database, large fixture), share it across a test suite with it.layer: 

import { it, layer } from "@effect/vitest"
import { Context, Effect, Layer } from "effect"

class Counter extends Context.Service<Counter, {
  readonly get: Effect.Effect<number>
  readonly inc: Effect.Effect<void>
}>()("Counter") {}

const CounterLive = Layer.sync(Counter, () => {
  let count = 0
  return {
    get: () => Effect.succeed(count),
    inc: () => Effect.sync(() => void count++)
  }
})

// Without it.layer: each test gets its own Counter (count starts at 0)
it.effect("starts at 0", () =>
  Effect.gen(function* () {
    const c = yield* Counter
    expect(yield* c.get).toBe(0)
  }).pipe(Effect.provide(CounterLive))
)

it.effect("increments to 1", () =>
  Effect.gen(function* () {
    const c = yield* Counter
    yield* c.inc
    expect(yield* c.get).toBe(1) // passes — starts fresh
  }).pipe(Effect.provide(CounterLive))
)

// WITH it.layer: all tests share the same Counter instance
layer(CounterLive)("shared counter", (it) => {
  it.effect("starts at 0", () =>
    Effect.gen(function* () {
      const c = yield* Counter
      expect(yield* c.get).toBe(0)
    })
  )

  it.effect("increments to 1", () =>
    Effect.gen(function* () {
      const c = yield* Counter
      yield* c.inc
      expect(yield* c.get).toBe(1) // passes — state is shared
    })
  )
  // Warning: ordering matters! Tests depend on shared state.
})
Per-test (default)Suite-shared (it.layer)
Layer builtEvery testOnce before all tests
CleanupAfter each testAfter all tests (afterAll)
State isolationYes — no cross-test leaksNo — state persists between tests
Use forCheap layers, stateful testsExpensive layers (DB, fixtures)

Pattern #5: Layer.fresh in shared suites

When using it.layer, you might want most layers shared but one layer rebuilt per test: 

layer(DatabaseLive)("with shared DB", (it) => {
  it.effect("test 1", () =>
    Effect.gen(function* () {
      const counter = yield* Counter
      yield* counter.inc
      expect(yield* counter.get).toBe(1)
    }).pipe(Effect.provide(Layer.fresh(CounterLive)))
    // ↑ Counter is fresh, Database is shared
  )

  it.effect("test 2 — counter starts at 0 again", () =>
    Effect.gen(function* () {
      const counter = yield* Counter
      expect(yield* counter.get).toBe(0) // passes — fresh ()
    }).pipe(Effect.provide(Layer.fresh(CounterLive)))
  )
})

Pattern #6: it.live — without test services

it.live runs tests with the real runtime services (real clock, real console), no TestEnv overrides. Useful for integration tests: 

it.live("integration test", () =>
  Effect.gen(function* () {
    const db = yield* Database
    const result = yield* db.query("SELECT NOW()")
    expect(result).toBeDefined() // real query against real DB
  }).pipe(Effect.provide(RealDatabaseLayer))
)

The testing toolkit summary

ToolWhat it doesWhen
Layer.mock(tag, partial) Partial mock — only stub what you use Fast unit tests
Layer.succeed(tag, impl) Full test implementation In-memory services
Layer.sync(tag, factory) Lazy stateful mock Stateful test services
it.effect(name, fn) Run Effect in test, auto-Scope Every test
it.layer(layer)(name, fn) Share layer across suite Expensive setup
Layer.fresh(layer) Force rebuild in shared suite Stateful services in shared suite
it.live(name, fn) No TestEnv, real runtime Integration tests
Golden rule: Prefer per-test layers (it.effect + Effect.provide) unless you have a real reason to share. Test isolation prevents ordering-dependent failures. Only reach for it.layer when layer construction is genuinely expensive.
